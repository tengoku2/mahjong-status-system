# 実戦からの何切る（初期版）

2026-10-20。生成元の `NANIKIRU_SPEC.md` と、このチャットで確定した回答に沿った実装。

## 使い方

- 正常に検証した新規HTMLの通常更新から自動で候補を登録し、新規半荘のうち実際の対局日時が最新の1件から最大3問を投稿する。
- `/mjs mortal_nanikiru mode:latest`：最新半荘の未出題から最大3問。
- `/mjs mortal_nanikiru mode:past`：直近168時間の未出題全体から評価差順に最大3問。
- `/mjs mortal_nanikiru mode:retry`：保存済みの投稿待ちセットを再開・履歴照合する。別の問題への差し替えは行わない。
- 手動コマンドはまどろみの運営・開発者向け。投稿先・結果先は既存 `/mjs nanikiru_config` の設定を再利用する。
- 牌を選ぶと、その本人だけに選択・Mortalの最大Q値の打牌・実戦の打牌を表示する。赤5は通常の5と別の選択肢。
- 24時間以内は回答を変更でき、変更前の回答も回答者ごとに保持する。締め切り後の公開結果は回答分布のみ。
- 回答後のボタンで「考えどころがある／単純な整理に感じる／情報が足りない」を保存できる。

## 初期の候補判定

`shape-1.0.0`。純粋な打牌判断で、手牌・副露・打牌候補が完全な局面だけを扱う。リーチ判断・鳴き判断・欠けた副露牌を推測して補う局面は対象外。

最小向聴数を達成する手牌分解から両面形・辺張形・対子の残し方を比較する。最小向聴数が同じ形の分岐と、聴牌維持／1向聴での形の比較を暫定的に拾う。Mortalの最大Q値の候補が孤立牌整理だけなら除外する。巡目や評価差に足切りを設けず、差が0の局面も含める。

これは形による候補抽出であり、受け入れ枚数・和了率・打点・危険度は算出していない。policyを和了率に読み替えない。牌の安全度やドラに関わる分岐の網羅は初期版の対象外。フィードバックを見ながら更新する。

問題には手牌・副露／槓・局・巡目・自風・局開始時点の点数を表示する。ドラ・河・他家副露は省略した復習問題であることを明記する。最大Q値が完全同値なら全てを比較先に表示し、僅差を誤答と断定しない。同一局の問題数制限は設けない。同点時は対局日時の降順・安定した問題IDの昇順。

## 保存と再試行

- 既存PostgreSQLに追加した `MortalReview`・`MortalCandidate`・`MortalBatch`・`MortalAnswer`・`MortalFeedback` に保存。既存の何切る／対局テーブルは変更しない。
- 出題状態は `issuedAt` の有無による未出題／出題済み。セット予約と送信処理の状態は別項目。投稿成功後に限って出題済みになる。
- 同じゲームの同じ席は、ファイル名・保存時刻・reviewer版・temperatureに依存しないID。同じ取り込み集合の再実行は同じセットを返す。
- PostgreSQLのトランザクションとアドバイザリロックで取り込み・選定を直列化する。候補は原子的に送信担当を1つに絞る。
- Discord POSTには固定nonceと `enforceNonce` を使用。送信成功後のDB保存失敗は、投稿の固定識別子をチャンネル履歴から探して復旧する。
- 通信タイムアウトなど送信結果が不明な問題は予約を維持し、存在を証明できるまで再送を保留する。Discord側のnonce保護には時間制限があるため、長時間後に盲目的な再送はしない。履歴権限がない・投稿が削除された等の場合は運営による確認が必要。
- 予約済みでも送信時点で168時間を過ぎたら投稿しない。セットと候補は保持し、別候補に差し替えない。
- 締め切り処理は起動時と30秒ごとの処理で復旧し、結果メッセージにも同じ重複防止を適用する。

## 生成元との接続

`POST /api/mortal-nanikiru/import`。既存 `EXTERNAL_API_KEY` のBearer認証が必要。まどろみ専用で、リクエストから投稿先ギルドを変更できない。最大16MiB、入力検証後に保存する。HTML・DB・ファイルパス・policyはこのAPIへ送らない。

生成元の `nanikiru_publish.py` は検証済みの判断から完全な打牌局面だけを送る。初回は `--baseline` で既存のデータを登録し、既存分から自動投稿しない。以後、通常の `analyze_reviews.py` の成功時に同期する。Web同期とは独立した保存待ちキューを持つ。送信失敗時のJSONは `.cache/nanikiru-publish/pending.json` に保持し、次回は同じJSONを先に再送する。

受領済みの対局IDを生成元にも保存し、以後の更新では新規分だけを送る。蓄積した全対局を毎回アップロードしない。

接続設定・APIキー・既存の本人データの指定は生成元 `.private/nanikiru-publish.json` に置く。収集元のアカウントとキューの紐付けを照合し、それ以外の新規手動インポートを自動では混ぜない。キューに紐付かない既存本人データは明示したIDだけを許可する。

通常の自動連携は生成元の既定DBと `analysis/` への正常生成時だけに限定する。テストや別出力先の生成からは投稿しない。再同期は `python -X utf8 nanikiru_publish.py`。

実データ・接続設定・圧縮／暗号化したデータを公開GitやDockerイメージに含めない。既存Koyeb Freeインスタンスと既存DBを利用し、追加サービス・有料インスタンス・ボリュームは作成しない。

## 検証

`npm test`、`npm run build`、生成元の `python -X utf8 -m unittest discover -s tests`。

`npx tsx scripts/check-mortal-nanikiru.ts` はDB内に新しい使い捨てスキーマを作成し、マイグレーション・実際の排他ロック・同時取り込み・最新／過去選定・履歴保持を確認して削除する。既存アプリのテーブルは変更せず、Discord投稿も行わない。
